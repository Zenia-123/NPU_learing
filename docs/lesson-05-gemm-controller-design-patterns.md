# 从 gemm_ctrl 提炼控制与功能模块的RTL设计方法

> 用途：把已经读过的代码转化成以后可以自己使用的设计方法。先确定硬件资源和数据流，再定义变量、事务完成事件、状态机和时序。
>
> 依据：用户上传的 `gemm_ctrl.sv`；已确认与此前读取的上游版本内容相同。对应上游固定提交：[8216c22](https://github.com/harishsg993010/tiny-NPU/blob/8216c22b762011aa20c05fc2768423fd12dda59d/rtl/gemm/gemm_ctrl.sv)。整理日期：2026-10-28。本文是设计总结与源码分析，未修改RTL，未新增HDL仿真结论。

## 1. 用一句话说明这个模块

`gemm_ctrl`把一条“计算C=A×B”的命令，拆成若干次子块事务，安排数据装载、阵列计算、部分和合并以及最终写回，并在全部完成后报告done。

它可以理解为“带数据通路的状态机”。文件里既有状态与地址控制，也有输入缓冲、结果选择、部分和加法和数值转换，不能仅根据ctrl这个名字认为它只有控制信号、完全没有数据处理。

### 1.1 先确定硬件位置

| 资源 | 位于哪里 | 保存/处理什么 |
|---|---|---|
| 数据SRAM | 控制器之外，由端口连接 | A、B和最终C |
| buf_a/b及FP16版本 | gemm_ctrl内部声明的存储数组 | 当前输入子块 |
| 数据选择与地址生成 | gemm_ctrl内部组合逻辑 | 哪个缓冲元素送到哪里、读写哪个地址 |
| PE阵列与局部ACC | 控制器之外的systolic_array | 当前K块的乘加 |
| 外部ACC SRAM | 阵列和控制器之外的独立存储模块 | 跨K块的旧部分和 |
| 结果合并与转换 | gemm_ctrl的STORE数据通路 | 选择PE结果、合并旧和、转换后写出 |
| 状态和各种游标 | gemm_ctrl内部寄存器 | 任务进度、位置、字节与拍号 |

“模块内部/外部”是RTL层次关系；不能据此确定芯片版图上的坐标。输入buffer最终如何映射为寄存器或存储结构，要结合端口需求、复位方式和综合结果判断。

### 1.2 逻辑只有两层循环

外层是整条命令的分块循环：M块→N块→K块，其中K最内层。内层是一个tile的完整事务：准备→装A→装B→清零→流式计算→保存结果。

| 状态 | 核心职责 | 结束依据 |
|---|---|---|
| IDLE | 接收并保存命令 | 命令在空闲状态被接受 |
| SETUP | 计算总块数 | 一拍准备完成 |
| TILE_SETUP | 算有效尺寸与基址，初始化局部游标 | 一拍准备完成 |
| LOAD_A/B | 将输入元素搬入buffer | 最后一个有效元素完整返回 |
| CLEAR | 清PE的旧ACC，准备流式计数 | 清零控制已按固定时序发出 |
| STREAM | 按偏斜规则选buffer数据，末尾排空 | 计数达到控制器末拍编号 |
| STORE | 保存部分和或最终输出 | 最后一个输出元素完整处理 |
| TILE_NEXT | 推进K/N/M块号 | 有下一块就继续，否则完成 |
| DONE | 发出命令完成状态 | 一拍后回IDLE |

## 2. 最重要的方法：先拆事务，再选状态和计数器

一个元素可能包含多个字节，一个块包含多个元素，一条命令又包含多个块。把它们混在一个“当前进度”里，是控制代码容易失控的原因。

建议先写出事务层次：

| 层次 | 何时完成 | gemm_ctrl的相关变量 |
|---|---|---|
| 一次接口传输 | 一个读返回值被捕获，或一个写数据被端口接收 | load_phase、store_phase等 |
| 一个元素 | INT8一个字节；FP16低高字节都完整处理 | load_byte、store_byte、lo_byte |
| 一个tile | 当前有效范围内所有输入/输出处理完 | load/store行列、eff尺寸 |
| 一条命令 | M/N/K方向所有tile执行完 | tile索引与总块数 |

由内向外定义完成：字节完成，才考虑元素完成；元素完成，才推进坐标；最后坐标的元素完成，才结束tile；最后tile完成，才结束命令。

这比先堆一个大case，再不断往里补条件，更容易保持正确。

## 3. 方法一：写RTL前先写“模块契约”

模块契约就是明确：什么时候可以接任务、对方需要保持什么、什么时候算做完。

至少回答下面几项：

| 要确定的问题 | 当前项目的实际约定 |
|---|---|
| 如何接收命令 | 只在IDLE且cmd_valid有效时接收 |
| 命令是否需要锁存 | 需要，保存为r_src、r_M/N/K、r_dtype等 |
| 读取多久返回 | 当前控制器按固定读时序，使用请求/捕获phase |
| 写端口是否可能拒绝 | 当前控制逻辑没有写ready等待分支，假定可按拍写入 |
| 结果格式是什么 | INT8路径32位累加，最终写8位；FP16路径用32位浮点编码累加意图，最终写两个字节 |
| done表示什么 | 当前控制器所有tile的存储步骤已经完成，进入DONE状态 |
| 支持什么范围 | 需由缓冲容量、计数位宽、硬编码16和地址空间共同限制，不能只看cmd字段位宽 |

设计新模块时，应把这些约定写在模块说明里。模块输入端口有valid，并不自动意味着已经实现了可停顿、可排队的握手协议。

如果未来连接可能停顿的接口，可以定义valid/ready：valid表示当前数据有效，ready表示下游本拍可以接收，二者同时为1才完成传输。若连接AXI等带独立响应的协议，还要区分请求被接收与事务最终完成，不能把任意ready都当成写入已完成。

## 4. 方法二：先设计数据通路，再写状态机

先回答“数据要经过哪些硬件”：

1. 数据源在哪里、一次能读多少位？
2. 需要什么缓冲、能同时提供几路数据？
3. 计算单元一次接收几项，结果延迟几拍？
4. 部分结果要不要跨批次保存？
5. 输出每拍能送多少位，是否需要格式转换？

然后每个状态才有明确任务：控制读端口、写buffer、驱动阵列、选择结果或写存储。

例如当前项目8位数据SRAM接口无法在装载时每拍直接提供阵列需要的多路操作数，因此先装入buf_a/b，再在STREAM阶段并行选择。FP16分成两个字节，也是接口8位、元素16位带来的数据通路要求，不是因为状态机喜欢多写一个状态。

一个组合索引表达式意味着选择电路；一个时钟沿赋值意味着需要保存状态；一次函数调用可能意味着组合算术。写RTL时，要能把表达式还原成这些硬件。

## 5. 方法三：变量必须先分类、写清单位和生命周期

### 5.1 按硬件作用分类

| 类别 | 变量示例 | 设计时问什么 |
|---|---|---|
| 命令快照 | r_src0、r_M、r_dtype | 接收后上游改变输入，会不会影响当前任务？ |
| 当前配置 | m_eff/n_eff/k_eff、tile_base | 当前块与整张矩阵有什么区别？ |
| 层级进度 | tile索引、load/store行列 | 哪个完成事件使它前进一步？ |
| 拍内阶段 | load_phase、store_phase、load/store_byte | 当前元素还差哪一步才完整？ |
| 数据存储 | buf_a/b、lo_byte | 谁写入、谁读取、有效范围是什么？ |
| 时间计数 | stream_cnt/total | 统计周期、操作次数还是数据个数？从0还是1开始？ |
| 组合派生 | idx_a/b、first/last_k_tile、acc_elem_addr | 是否能由已有寄存器直接算出，不需要再保存？ |

不要把每一个名字都做成寄存器。可由现有状态直接组合推导的量，通常不必额外保存；若为缩短组合路径而寄存，还必须处理新增的一拍以及控制对齐。

### 5.2 单位必须进入说明，必要时进入名字

| 数值 | 单位 |
|---|---|
| 数据SRAM地址 | Byte地址 |
| 外部ACC SRAM地址 | 32位元素地址 |
| DATA_W、ACC_W | bit |
| load_row/col | 元素坐标 |
| stream_cnt | 当前流式周期编号 |
| stream_total | 最后周期编号，当前代码不是总周期数 |

例如地址公式应先写成数学量：

$$addr_{byte}=base_{byte}+(row\times stride_{elem}+col)\times bytes\_per\_elem+byte\_sel.$$

确认单位后，再转换成移位、拼接等RTL。这样能避免把bit宽、Byte数、元素数量和索引位宽混淆。

更清晰的命名可以是 `stream_last_idx`、`row_stride_bytes`、`elem_count`。名字不能替代注释，但能减少误读。

### 5.3 生命周期决定何时初始化

| 变量生命周期 | 典型变量 | 何时初始化 |
|---|---|---|
| 一条命令 | r_字段、总tile数 | 接受新命令时 |
| 一个tile | 有效尺寸、基址、load/store游标 | TILE_SETUP |
| 一个元素 | byte/phase、低字节暂存 | 新元素开始或当前元素完成后 |
| 全局运行状态 | FSM | 复位时，之后正常转移 |

每个寄存器都应说清四件事：何时装入初值、何时更新、何时保持、何时不再有效。

## 6. 方法四：用“完成事件”驱动进度

当前INT8直接写SRAM时，每个STORE周期都成功写出一项，因此坐标可以每拍推进。但更通用的原则是：

> 计数器随对应事务真正完成而推进，而不是只因为时钟过去了就推进。

用概念事件说明各层关系（这些事件名是设计建议，不是原文件已有变量）：

| 建议事件名 | 意义 | 应更新什么 |
|---|---|---|
| cmd_accept | 新命令被接受 | 锁存命令、开始新任务 |
| rd_byte_done | 一个字节返回并被保存 | 更新byte/phase或低字节暂存 |
| load_elem_done | 一个完整元素装入缓冲 | 推进load坐标 |
| store_elem_done | 一个完整元素写回步骤结束 | 推进store坐标 |
| tile_done | 最后坐标的元素也已完整处理 | 推进tile索引或准备下一块 |

FP16的第一字节完成时，只应改变byte标志，不应提前推进元素坐标；读改写的读请求发出时，也不能当作结果已经写回。

固定时延接口可由phase推导完成事件；可停顿接口应以返回valid、传输握手或相应响应为依据。

### 6.1 可复用的行列遍历写法

下面只是坐标更新片段，不是完整可编译模块。假设row/col为寄存器，rows/cols是已经锁存的正有效尺寸，elem_done只在一个完整元素成功处理的沿有效：

```systemverilog
if (elem_done) begin
    if (col == cols - 1) begin
        col <= '0;
        row <= row + 1'b1;
    end else begin
        col <= col + 1'b1;
    end
end
```

INT8、FP16、DMA搬运都可以使用这种遍历结构，区别是怎样定义elem_done。最后元素完成时还要同步离开遍历状态，或者显式把游标保持在末项，不能在下一拍继续访问越界位置。

若采用valid/ready写数据流，通常先定义：

```systemverilog
assign wr_fire = wr_valid && wr_ready;
```

在一个传输就对应完整元素的条件下，可用wr_fire驱动坐标更新；FP16窄接口要等最后一个字节的wr_fire才形成elem_done。停顿期间坐标、写地址和待写数据需保持稳定，数据来源也要保证不被改写。这只是数据流握手示意，不是完整AXI接口实现。

## 7. 方法五：明确三类职责，再选择过程块写法

gemm_ctrl实际有四个主要过程块，承担三类职责：

| 职责 | 原代码过程 | 应保存/驱动什么 |
|---|---|---|
| 保存当前状态 | 第143行always_ff | state寄存器 |
| 计算下一状态 | 第160行always_comb | state_next |
| 形成当前输出 | 第273行always_comb | SRAM端口、阵列端口、busy/done |
| 更新数据与游标 | 第440行always_ff | 命令字段、缓冲、各种计数和位置 |

前三项中“下一状态”和“当前输出”都属于组合决策；状态与数据寄存器负责保存。学习重点是职责边界，不是强制每个工程都必须恰好写三个或四个always。

### 7.1 组合逻辑：默认值完整，覆盖有依据

`state_next=state`表示默认停留；读写使能默认0表示没有命中的状态不发访问请求；每个组合输出都要在所有路径有定义。

不要在组合块里用“漏赋值”表示希望它记住上拍数据，那会引入锁存器或造成意外行为。需要跨周期记忆，就明确声明寄存器并在时序块保存。

### 7.2 时序逻辑：明确更新条件，其他时候保持

时钟寄存器通常使用非阻塞赋值 `<=`；if或case没有命中时允许保持旧值。例如LOAD_B期间没有更新store坐标是正常的。

组合中间表达式通常使用阻塞赋值 `=`，让后续语句使用当前计算结果。但不要仅凭赋值符号推断最终硬件：声明类型、过程位置和跨周期使用方式都要一起看。更清晰的实现可以显式区分当前寄存器值q与组合下一值d。

### 7.3 控制状态与数据有效必须同时对齐

某个状态在沿后切换，不代表沿前驱动的数据已经属于下一状态。以STORE为例：

| 时刻 | 行列号/写接口 |
|---|---|
| 沿前 | 当前坐标形成当前地址和数据 |
| 上升沿 | SRAM采样当前写数据；控制器按旧坐标决定下一坐标 |
| 沿后 | 寄存器更新；组合电路准备下一元素 |

最后元素也一样：沿前仍是STORE且写使能有效，最后写入与state进入下一状态发生在同一沿。不能因为state_next已经是下一状态，就在组合输出里提前撤销最后一次写使能。

## 8. 方法六：完成条件和计数范围要先推导再写代码

### 8.1 每个done都要有清楚的结束事件

计算任务中可能有多个不同终点：最后输入被接收、最后乘积采样、最后ACC更新、最后输出送出、最后存储响应完成。必须写清模块done承诺哪一个。

本项目通过固定的STREAM长度等到阵列结果完成，再进行STORE。阵列的acc_valid没有K输入，而且在所读封装中未使用，不能仅凭名字就将它接成整次GEMM的done。

设计自己的模块时，如果结束时间确实固定且有证明，可以使用延迟计数；若会遇到停顿、不同计算延迟或不确定响应，更适合让完成事件或valid随数据/事务传播，并累计最后一项是否完成。

### 8.2 统一“总数量”和“最后编号”

若计数从0到L且包含L，则共有L+1拍。当前 `stream_total=k_eff+m_eff+n_eff-1`，实际STREAM槽数是k_eff+m_eff+n_eff。

两种设计都可以，但不要混用：

| 变量保存什么 | 结束判断举例 |
|---|---|
| 最后编号last_idx | 当前idx==last_idx，且本项完成 |
| 总数量count_total | 当前idx==count_total−1，且本项完成 |

最好把初值、第一次动作、最后一次动作及退出沿列成小表，检查有没有少一项或多一拍。若依赖旧值比较后再更新，更要按沿前值推导。

### 8.3 区分索引位宽与数量位宽

16个位置的下标是0～15，4位足够；“有效数量16”至少需要5位。需要表示0～32的计数器也不能只用5位。

常见参数关系可写为：

```systemverilog
localparam int IDX_W = (MAX_ITEMS <= 1) ? 1 : $clog2(MAX_ITEMS);
localparam int COUNT_W = $clog2(MAX_ITEMS + 1);
```

这里假定MAX_ITEMS为正整数；IDX_W给“0到MAX_ITEMS−1的索引”，COUNT_W给“0到MAX_ITEMS的数量”。如果游标需要表示末项之后的哨兵值，也要额外考虑范围。不能把所有与16相关的变量都机械定成4位。

当前总tile数只有4位，因此16个tile会截成0。设计参数化模块时，数组大小、tile步长、索引位宽、计数位宽及地址宽度必须一起推导。

## 9. 方法七：让模式差异停留在最小必要层次

当前文件在转移、输出、时序更新中分别判断dtype、multi_k、first/last_k、byte与phase，随着功能增加，组合情况会迅速增长。

更容易扩展的思路是分层：

| 层次 | 负责什么 | 尽量不关心什么 |
|---|---|---|
| 命令层 | 接受命令、管理整次任务、报告done | 某个FP16字节的具体位置 |
| tile层 | 计算尺寸/基址，安排装载、计算、写回 | 一个元素需要几次总线传输 |
| 元素搬运层 | 低高字节、请求/返回、格式转换 | 整个矩阵有多少M/N块 |

元素搬运层对外给出“这个元素完成了”，上层就能使用相同的行列遍历逻辑。

规模小的模块可以保持在同一个文件中，通过局部事件与清晰分组实现；确实需要复用、独立验证或改善时序时，再拆成子模块。不是每个phase都必须新建模块，也不必让整个系统每遇到一种精度都复制一套大状态机。

数据数值格式同样需要明确边界：INT32位模式的 `+` 是整数加法，FP32编码不能直接复用这个运算表达式。控制流程相同，不代表算术运算也可以不区分类型。当前FP16跨K合并处的普通加法是不能直接照搬的实例。

## 10. 方法八：复位、有效性、资源与时序一起考虑

### 10.1 不要机械复制“大buffer全部异步清零”

控制状态、有效标志和游标一般需要确定初值；大型数据buffer是否需要复位，要根据目标存储和有效性协议决定。若有效位置保证先写后读，可以通过复位控制/有效信息而不清所有数据位，减少复位资源并更利于存储推断。

前提是你能证明未写位置不会被当成有效输入。当前控制器使用eff与idx范围屏蔽无效位置，这种“有效范围”思想值得保留，但不能在没有分析连续tile行为之前直接删除任何复位或清零。

### 10.2 按寄存器路径检查控制和数据是否对齐

每新增一级数据寄存器，都要一起考虑：数据、valid、clear、dtype、地址/标签和完成时间是否仍对应同一批操作。只延迟数据、不延迟控制，或只把结束计数加一而没有修复操作数对齐，都可能出错。

同样，`always_comb`或函数中的乘法、移位、浮点运算并不意味着物理时间为0。它们必须在一个时钟周期内满足传播时延要求；必要时分级寄存，同时调整控制。是否满足频率，要看综合和静态时序分析，而不是只看功能仿真的周期数。

### 10.3 参数化必须覆盖所有相关结构

如果希望改变阵列规模，不能只把ARRAY_M/N改成参数：tile计数、固定16的步长、缓冲K容量、低4位索引、ACC SRAM深度、流式计数上界都需要同步改变。

如果改变数据接口宽度，也要同步改变每元素传输次数、字节选择、地址增量、缓冲装配和返回时序。当前FP16低高字节组织源自8位接口，不应在16位或32位接口上无条件复制。

## 11. 功能正确之后，再根据硬件成本优化

当前阶段顺序执行，单tile、单K块、固定时序下可先估计：

$$T_{\mathrm{tile}}\approx T_{\mathrm{fixed}}+
2b(mk+kn)+(k+m+n)+bmn,$$

其中b是每元素字节数（INT8为1、FP16为2）；装载因请求/捕获安排每字节用两个周期，STORE此处只指单K块最终输出；还未加入跨K部分和处理，算术正确性也要另行验证。

这个模型能提示瓶颈来自装载、阵列还是写回。之后再考虑：

- 提高存储端口宽度或并行供数能力。
- 使用双缓冲，确实允许下一块装载与当前计算重叠。
- 让PE的ACC跨K块保留结果，减少部分和往返，但需要重新设计清零与完成语义。
- 用递增地址寄存器替代部分复杂组合地址运算，同时正确处理行末跨度。
- 拆分或流水化较长的数据与控制组合路径。

每种优化都需要相应的资源、端口、仲裁或依赖管理，不能仅凭新增一个buffer就把LOAD和COMPUTE的时间自动改成取最大值。

这也可用于后续CIMFlow/PE性能建模：读、计算、写、部分和搬运分别对应哪些硬件事件，哪些真实重叠，应由实际结构决定；不要为了简化模型而把某一项成本无依据地隐藏进另一项。

## 12. 写完后怎样检查，不只看最后矩阵对不对

| 检查对象 | 要成立的关系 |
|---|---|
| 命令保存 | 忙期间改变上游cmd输入，不影响已经接收的命令 |
| 索引与地址 | 发访问时索引合法，Byte地址与元素地址不混用 |
| 元素完整性 | FP16每元素的高低字节恰好各一次，读改写不重复加和 |
| 推进条件 | 没有完成当前元素时，行列不提前变化；接口停顿时保持位置和待发数据 |
| 输出数量 | 单K块最终输出字节数等于m_eff×n_eff×b |
| 输入数量 | 本tile装载字节数分别等于m_eff×k_eff×b、k_eff×n_eff×b |
| 最后一项 | 最后一项真正写入/完成以后再报告该级结束 |
| 连续任务 | 一个tile/命令残留的计数、byte、phase和旧ACC不会污染下一次 |
| 数值语义 | 整数与浮点分别使用正确运算、转换和溢出规则 |

边界例子应覆盖尺寸1、刚好整块、比整块多1、非整块M/N/K、K分块，以及接口可能停顿和连续命令等行为。若接口不支持停顿，应明确写入契约，不能把不支持描述成已经通过停顿测试。

验证应分成两类：数学参考检查输出值；时序/协议检查访问数量、地址顺序、推进条件和done时刻。最终值碰巧正确，不足以证明中间没有越界访问或重复写入。

## 13. 以后自己设计模块时的实际工作顺序

1. **写任务和契约。** 输入什么、输出什么、什么时候接受、什么时候完成、允许什么延迟与停顿。
2. **画硬件图。** 标清数据存储、计算单元、缓冲、接口位宽及跨周期寄存器。
3. **列变量表。** 为每个变量写类型、单位、范围、生命周期和更新事件。
4. **拆事务层次。** 字节/元素/块/命令分别怎样完成，哪些地方必须等待。
5. **列周期表。** 至少推演一次请求返回、一次流水排空、一次最后元素退出。
6. **画状态转移。** 每个状态有明确资源动作、停留依据和退出事件。
7. **组织RTL。** 状态保存、组合决策/输出、数据更新职责分开；精度或接口差异在明确层次处理。
8. **检查正确性，再优化。** 先保证事件、地址、数量和数值都正确，再讨论重叠、资源共享与频率。

值得从gemm_ctrl学走的核心，是“把一次大任务拆成有明确数据位置、推进事件与完成边界的多层事务”。具体的状态名、固定16和某些原码表达式只是这个项目的实现，不是以后必须照抄的模板。
