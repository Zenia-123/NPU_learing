# tiny-NPU 硬件与代码讲解要求

更新日期：2026-11-10。本文件记录用户对后续 tiny-NPU 学习对话的长期讲解要求。具体问题和用户当次的明确指令优先；课程项目主线与开放作业支线按各自交接记录推进。

用户原话：“以后按照上述的要求讲解代码（按照程序顺序，先讲清楚逻辑再讲清楚代码）。但是当讲解一个新的模块的时候，还是需要先讲清楚硬件结构，数据流、控制流、指令流等以及相关的硬件和架构知识，再讲解代码。”

## 一、先区分当前请求

- 用户问一个具体信号、代码片段或不理解的步骤时，先直接解决该问题，补充理解所必需的局部硬件背景；不要默认重讲整门课或直接切换到下一讲。
- 开始一个新模块时，先介绍该模块需要的硬件和体系结构知识，再按源文件顺序进入代码。
- 继续已开讲模块时，从当前停点继续；必要时简短回顾上下文，不重复已经解释清楚的内容。
- 用户要求快速概览、只解释某段、分多次学习或指定其他范围时，按用户本次要求调整深度与顺序。
- “已经讲过”不等于“用户确认掌握”；不以已讲解代替对其理解状态的判断。

## 二、新模块：代码之前先建立硬件认识

按模块实际内容组织，可分多次讲清楚：

1. **问题与前置知识**：说明模块解决什么问题，补足当前模块必需的硬件原理、体系结构、协议或数据表示知识。用户尚未学过的概念从基础解释。
2. **系统位置与模块关系**：说明该模块在 tiny-NPU 中的位置；上游、下游、控制器、存储体和计算单元如何连接，明确它们分别负责什么。
3. **整体硬件结构**：结合实际RTL，说明真正存在的寄存器、存储阵列、组合运算、选择器、状态机、握手与接口。用规整、清楚的硬件图或必要时用表格展示。
4. **数据流**：从数据产生/存储位置讲到传输、变换、使用和写回；明确数据宽度、格式、顺序、地址和单位。
5. **控制流**：解释使能、启动/完成、状态转移、计数器、条件、仲裁、valid/ready、反压和错误等怎样控制硬件，区分请求、接受和完成。
6. **指令流**：模块涉及指令时，说明指令从哪来、如何获取/解码/派发、字段如何影响控制、完成和依赖。与模块无直接关系时明确边界，不虚构指令路径。
7. **关键变量与接口**：说明端口、参数、寄存器和重要组合信号的名称、输入/输出方向、位宽、符号属性、单位、物理意义、复位值/生命周期、有效条件和更新时机。区分Byte地址、字/条目地址、bit、beat、周期和计数器编码。

硬件结构、数据/控制/指令流和相关基础知识应先于源代码逐段解说；变量可在相应硬件或代码首次出现前后集中整理，但不得漏讲理解所需的变量。

## 三、按源代码顺序讲：每段先逻辑，再代码

对用户要精读的真实源码，先确认文件、版本、相关上游/下游实例和当前学习停点，再按原文件出现的顺序分段。一个常见顺序为：模块声明与参数→端口→内部信号→组合计算→状态机及寄存器→数据通路→接口输出；实际顺序以真实文件为准，不为套模板改变源码顺序。

对每个代码段，按以下次序讲解：

1. **先说明本段的逻辑和硬件目的**：要完成什么动作、为什么需要、输入从哪来、结果给谁、影响哪些状态和数据。
2. **解释涉及的变量**：真实名称、位宽、单位、物理含义、值在哪个条件和时钟沿发生变化。对新出现的变量逐项解释，已经说清的变量不反复堆砌。
3. **展示相关代码并逐句解释**：说明表达式、分支条件、运算、赋值和语法如何实现上面的硬件逻辑；解释关键SystemVerilog/Verilog语法，不只把每行翻译成中文。
4. **对应硬件和事件**：指出寄存器、组合逻辑、比较器、计数器、多路选择器、存储端口和控制条件；必要时推导地址公式、数据取位与边界。
5. **说明时序与交互**：何时采样、沿前是什么、沿后变成什么；哪些动作因同一个握手或完成事件发生；数据暂停时哪些信号保持。

严格区分“按源文件顺序讲解”和“硬件逐行顺序执行”：多个assign/always_comb/always_ff等并发作用；时序块同一沿读取沿前值，结合非阻塞赋值解释新值何时可见。

## 四、贯穿具体数据与周期例子

- 选与该模块真实功能对应的一个具体小例子，明确参数、初始值、数据、地址及单位，贯穿相关代码，展示变量如何变化。
- 需要时列逐拍表或时序波形：时钟沿前状态/输入、是否真正握手、本沿操作、沿后寄存器/输出；说明假设和等待周期。
- 对同步SRAM说明读地址采样、dout沿后更新与下游时序寄存器捕获的关系；对valid/ready说明未握手时数据、控制、索引如何保持。
- 区分命令完成、beat/burst完成、本地存储写入完成和结果可消费等不同事件，结合真实代码解释。
- 涉及分块、矩阵索引或多维地址时，用具体形状、步长、数值和单位代入；必要时说明边界、尾项、精度、符号位和数据宽度。
- 逐拍推导是分析结果，不得冒充实际仿真波形；只有真实执行后才能报告编译、仿真和波形观察结果。

## 五、来源与真实性

- 优先阅读并链接实际源码；标明仓库、文件路径及核对的commit或版本。若实际代码不同于历史讲义，以当前核对的代码为准并解释差别。
- 区分真实存在并连接的硬件、占位逻辑、未连接/未使用信号、软件仿真Shim与为教学提出的假设设计。不能把预期架构或建议实现说成已集成、已仿真。
- 明确综合与仿真的差异；如发现源码边界、未使用变量或潜在问题，说明触发条件与证据，不把有限例子当作穷举证明。
- 若源码或必要上下文不可用，要如实说明阅读范围；禁止编造变量、行为、测试结果或GitHub提交。

## 六、协作和沉淀

- 使用中文，面向RTL基础仍在建立中的学习者解释；先硬件实体和因果关系，再解释语法。
- 不擅自布置额外练习；用户要求动手时按既定协作方式一步步进行。
- 开放作业支线的用户亲自编写、保存、编译和运行要求继续适用；未经用户明确要求，不代替用户执行实验或宣称其已掌握。
- 每次完整的tiny-NPU主线讲解按既有约定保存完整Markdown到本仓库 main 分支的 npu_docs/，同步后给出文件链接和真实commit；同步失败时说明具体状态，不声称已经上传。
- 保留作业代码、讲义、测试、波形及不同学习线的独立进度；保持npu_docs/handoff-tiny-npu-mainline.md与根目录HANDOFF.md中的相关进度准确。
- 后续对话先阅读根目录HANDOFF.md、主线交接和本规范，根据用户最新请求决定停点；当前请求和用户后续明确要求优先于旧计划。
